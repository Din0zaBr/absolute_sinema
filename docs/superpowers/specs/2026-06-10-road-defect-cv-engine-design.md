# Дизайн: CV-движок анализа дорожных дефектов

**Дата:** 2026-06-10
**Статус:** утверждён к реализации (подсистема 1 из 5)
**Автор:** Claude (по итогам брейншторма с заказчиком) + фоновый research-воркфлоу `road-defect-cv-research`

---

## 1. Контекст и назначение

По фотографиям российских дорог нужно автоматически определять дорожные дефекты
(ямы/выбоины, трещины, заделки), их **форму**, **размеры** и **глубину**, классифицировать
по **серьёзности (ГОСТ Р 50597-2017)** и в перспективе — привязывать к **геолокации** и
**ответственному за участок**, которому уходит автоотчёт.

Итоговый продукт — **веб-платформа учёта дорожных дефектов**. Она состоит из пяти
подсистем; этот документ описывает **подсистему 1 — CV-движок**, фундамент всего остального.

### Декомпозиция системы и порядок сборки

| # | Подсистема | Зависит от | Этот спек |
|---|-----------|-----------|-----------|
| **1** | **CV-движок** (детекция, классификация, форма, размеры, глубина) | — | **да** |
| 2 | Backend API + БД (дефекты, участки дорог, ответственные) | 1 | позже |
| 3 | Веб-UI: загрузка + карта/дашборд | 2 | позже |
| 4 | Отчёты/уведомления ответственному | 2 | позже |
| 5 | Геолокация (EXIF GPS + проекция на дорогу) | 1 | позже |

Каждая подсистема получает свой цикл «спек → план → реализация». CV-движок проектируется
так, чтобы остальные подсистемы подключались к нему через стабильный JSON-контракт (см. §8).

## 2. Честные границы физики (определяют всю архитектуру)

Это зафиксировано на брейншторме и подтверждено ресёрчем. Архитектура построена вокруг этих
истин, а не вопреки им.

1. 🟢 **Детекция + форма/контур + классификация** — решаются на любом RGB-фото.
2. 🟡 **Размеры в сантиметрах (диаметр/длина/площадь)** — только при **масштабной привязке**:
   эталон известного размера в кадре (люк по ГОСТ, разметка) либо метрическая реконструкция.
3. 🔴 **Глубина в сантиметрах** — **невозможна по одному обычному фото**. 2D-маска + масштаб дают
   только размеры отверстия в плане, не вертикаль. Достоверная глубина — **только** из серии
   кадров (фотограмметрия/SfM) или датчика глубины. По одному фото — лишь относительная оценка
   («мелкая/средняя/глубокая»), которая **никогда** не выдаётся как ГОСТ-сертифицируемые см.

**Следствие — гибридный режим точности:** система всегда честно сообщает, что достижимо для
данного входа, и не выдаёт числа, которых физически не может знать.

## 3. Решения, принятые с заказчиком

- **Подход:** гибрид (предобученный детектор + сегментация + масштаб по эталону + относительная
  глубина) **плюс** опциональный фотограмметрический «точный режим» для серии кадров.
- **Модели:** только **готовые/предобученные**. Обучение с нуля — **нет**. Дообучение (fine-tune) —
  только как запасной путь, если точности не хватит, и на уже размеченных открытых данных.
- **Глубина** — через серию/SfM, а не из 2D-маски.
- **Масштаб** — через **гомографию** (ректификацию плоскости дороги), а не один коэффициент px→см.
- **Геолокация** — отдельной подсистемой позже; в MVP местоположение задаётся вручную.
- **Ресурсы:** ориентир — **CPU-only Windows**, готовые веса, инференс через ONNX.

## 5. Гибридная логика измерений

Конвейер для каждого фото: **детекция** (YOLOv12s, боксы + класс) → **сегментация** каждого дефекта
(MobileSAM по боксу → бинарная маска) → **дескрипторы формы** в пикселях → **разрешение масштаба**
в зависимости от сценария.

**Дескрипторы формы (пиксели, всегда), через `skimage.measure.regionprops`:**
- `area` (px²), `perimeter` (px)
- `equivalent_diameter_area = sqrt(4·area/π)` — это и есть отчётный «диаметр»
- `eccentricity` (0 = круг), `major/minor_axis_length`, `orientation`
- `solidity = area / convex_hull_area` — отчётная «выпуклость» (конвенцию указываем явно)
- При наличии масштаба длины × `mm/px`, площади × `(mm/px)²`.

### Сценарий A — одиночное фото, БЕЗ эталона
- **Диаметр/форма:** только в **пикселях** + безразмерные отношения (eccentricity, solidity) —
  они масштабонезависимы и выдаются как есть.
- **Размер в см:** **не выдаётся** (опционально грубая оценка при уверенной плоскости — с пометкой
  «ориентировочно»).
- **Глубина:** **не измеряется**; опционально Depth Anything + RANSAC-плоскость → относительный
  бакет «мелкая/средняя/глубокая», **никогда не в см**.
- **Уверенность:** отношения формы — средне-высокая; любой абсолютный размер/глубина — **очень
  низкая, см не показываем**.

### Сценарий B — одиночное фото, С эталоном
- **Масштаб:** детект эталона (люк через Hough-circle; либо ширина разметки), `mm/px = known_mm/px`.
  Первичный якорь — **лаз люка 600 мм**. Из эллипса люка восстанавливаем позу камеры и **гомографию**
  плоскости дороги → корректное измерение в любой точке кадра, а не один коэффициент.
- **Диаметр/ширина/площадь/длина:** дескрипторы × `mm/px`; сверка с порогами ГОСТ (§6).
  Надёжно при near-nadir и копланарности эталона с дефектом. Полоса ошибки **~±10–20%**.
- **Глубина:** по-прежнему **не восстановима** из плоского масштаба на одном кадре. Только
  относительная оценка с пометкой **низкой уверенности (±1–3 см)** — для приоритезации, не для
  сертификации ГОСТ ≥5 см.

### Сценарий C — серия кадров (подъезд/проезд)
- **Реконструкция:** hloc (DISK+LightGlue) → COLMAP CPU sparse (sequential matcher, overlap ~10,
  ~1000 фич/кадр, ratio 0.7, ≥30 inliers) → OpenMVS CPU dense.
- **Масштаб:** эталон в кадре (лаз 600 мм или ширина разметки) → метрический масштаб модели по двум
  точкам известного реального расстояния. EXIF/GPS — только метровый приор, не для см-глубины.
- **Глубина + объём:** сегментируем окружающее покрытие, RANSAC-плоскость, объём = 2.5D между
  плоскостью и дном; **глубина = макс. перпендикуляр от плоскости до дна**. Это **единственный
  сценарий с достоверными см глубины и объёмом**.
- **Уверенность:** длина/ширина/площадь — высокая; глубина/объём — средне-высокая (лучший
  рецензируемый кейс ~1% по объёму на контролируемой съёмке из 90 кадров; реальный drive-by — хуже,
  1% это потолок).
- **Протокол съёмки (зашить в подсказки приложения):** камера должна **смещаться** (чистый поворот
  ломает SfM); ~20–60 кадров, перекрытие 70–80%; снижать скорость; **косые взгляды внутрь полости**
  + разные высоты; держать эталон в нескольких кадрах.

### Сводка уверенности

| Величина | A (без эталона) | B (эталон) | C (серия) |
|----------|-----------------|-----------|-----------|
| Отношения формы (eccentricity, solidity) | средне-высокая | высокая | высокая |
| Диаметр/ширина/длина/площадь (см) | не выдаётся | **±10–20%** | высокая |
| Глубина (см) | не выдаётся | низкая (±1–3 см, ориентир) | **средне-высокая** |
| Объём | — | — | средне-высокая (~1–5%+) |

## 6. Эталоны и пороги ГОСТ (зашиваются в код)

**Якоря масштаба:**
- **ГОСТ 3634** круглый люк — **лаз 600 мм** = *первичный якорь* (стабилен для Л(А15) и Т(С250),
  суффикс «-60»). Крышка снаружи ≈ **646 мм**; опорная база ≈ **750–840 мм** по классу (сверять с
  изданием 89/99/2019 — стабилен только 600 мм; в части 3634-89 встречался лаз 550 мм). Явно решаем,
  что меряем: лаз 600 мм или обод крышки 646 мм.
  **Решено (2026-06-11, ревью реализации):** на дороге люк почти всегда ЗАКРЫТ, и контурный
  детектор видит наружный обод крышки, а не лаз — поэтому якорь по умолчанию в коде —
  **обод крышки 646 мм** (`reference.type = manhole_gost3634_cover`); 600 мм передаётся явно
  (`known_mm=600`), когда детектируется открытый проём. Кандидат Hough дополнительно
  подтверждается эллипсом контура (центр/диаметр согласованы), иначе масштаб не выдаётся —
  защита от ложного эталона (колесо, круглая яма, заплатка).
- **ГОСТ Р 51256-2018** разметка — *вторичный/подтверждающий* (зависит от категории, допуск ±0.01 м):
  линия 1.1 = **0.10 м** (0.08 кат IV; 0.15 кат IA); краевая 1.2 = 0.10–0.20 м; **СТОП-линия 1.12 = 0.40 м**.

**Пороги серьёзности — ГОСТ Р 50597-2017** (п. 5.2.4 / табл. 5.3; заменяет легаси «15×60×5 см» из 50597-93):
- Одиночный дефект (выбоина/просадка/пролом) **несоответствует норме при длине ≥ 15 см И глубине ≥ 5 см
  И площади ≥ 0.06 м²** (все три одновременно).
- **Сроки устранения (одиночные):** кат IA = 1 сут; IБ/IВ = 3; II = 5; III = 7; IV = 10; V = 12 сут.
- **Агрегированные мелкие на 100 м полосы:** > 0.1 м²/100 м (IA–IВ, 5 сут) … > 5.2 м²/100 м (V, 20 сут).
- **П. 4.4:** опасный несоответствующий участок обозначить знаками и при необходимости оградить
  **в течение 2 часов** с момента обнаружения.

**Следствие для движка:** длина/площадь решаются в B/C; нога «глубина ≥ 5 см» решается **только в C**
(или с датчиком). В A/B сверяем длину/площадь с ГОСТ, а глубину помечаем «не сертифицируемо — нужна
серийная съёмка».

## 7. Архитектура CV-движка (модули)

Каждый модуль — одна ответственность, тестируется изолированно, общается через типизированные данные.

```
src/road_defect/
  config.py     # константы ГОСТ, пути к весам, пороги, классы; единая точка правды
  pipeline.py   # оркестратор: фото|серия -> DefectReport (склеивает модули)
  detect.py     # Detector: фото -> [Detection(bbox, class, score)]
  segment.py    # Segmenter: фото+bbox -> mask (MobileSAM); + fallback Hough/threshold
  shape.py      # дескрипторы формы из маски (regionprops): area, eq_diameter, ecc, solidity...
  scale.py      # ReferenceScaler: детект эталона (люк/разметка) -> mm/px + гомография плоскости
  depth.py      # RelativeDepth: Depth Anything -> относит. бакет (опц.); интерфейс под метрику
  photogrammetry.py # SeriesReconstructor: серия -> метрич. облако -> глубина/объём (Сценарий C)
  severity.py   # классификация по ГОСТ Р 50597-2017 -> {conforming?, deadline_days, hazard}
  report.py     # сборка JSON-контракта + аннотированное изображение (overlay)
  cli.py        # CLI: папка/серия -> outputs/*.json + *_annotated.jpg
```

**Поток данных (одиночное фото):**
`image → detect → [для каждого дефекта: segment → shape] → scale(если эталон) →
depth(опц.) → severity → report(JSON + overlay)`

**Поток данных (серия):**
`frames → photogrammetry(SfM+scale) → 3D глубина/объём → severity(полный, с глубиной) → report`

Модели грузятся лениво и кэшируются; интерфейсы детектора/сегментатора/глубины абстрактны, чтобы
менять реализацию (Ultralytics .pt ↔ ONNX) без правок конвейера.

```json

    "homography_applied": true,
    "error_band_pct": 15
  },
  "defects": [
    {
      "id": 1,
      "class": "pothole",
      "confidence": 0.87,
      "bbox_px": [x, y, w, h],
      "mask_rle": "...",
      "shape": {
        "area_px2": 18420, "equivalent_diameter_px": 153,
        "eccentricity": 0.62, "solidity": 0.91, "orientation_deg": 12
      },
      "metric": {
        "available": true,
        "equivalent_diameter_cm": 43.5, "length_cm": 58.0, "area_cm2": 1487,
        "depth_cm": null, "depth_bucket": "medium",
        "depth_certifiable": false, "confidence": "medium", "error_band_pct": 15
      },
      "severity": {
        "standard": "ГОСТ Р 50597-2017",
        "length_exceeds": true, "area_exceeds": true, "depth_exceeds": null,
        "non_conforming": "indeterminate_without_depth",
        "repair_deadline_days": null, "hazard_signing_required": null,
        "note": "Длина и площадь превышают норму; глубину нужно подтвердить серийной съёмкой."

    }
  ],
  "location": {"available": false, "source": "manual_later"},
  "warnings": ["EXIF/GPS отсутствует", "эталон не найден в кадре"]

```

Этот контракт стабилен: backend (подсистема 2) пишет его в БД; reporting (4) рендерит человекочитаемый
отчёт; geolocation (5) заполняет `location`.

## 10. CPU/Windows: риски и митигации

| Риск | Severity | Митигация |
|------|----------|-----------|
| **Dense MVS только CUDA** (COLMAP PatchMatch, Meshroom) | высокий — блокирует объём в C | **OpenMVS** CPU dense; либо разреженное/триангулированное облако для near-planar ям; сборка из исходников / WSL2 |
| **Нет достоверной см-глубины по одному фото** | высокий — честность | жёстко гейтить см-глубину на Сценарий C/датчик; в A/B только относительные бакеты |
| **AGPL-3.0 через Ultralytics** | высокий (коммерция) | инференс через `onnxruntime` без импорта `ultralytics`; MobileSAM/SAM из Apache-репо; DISK+LightGlue вместо SuperPoint/SuperGlue |
| **Domain gap (нет РФ-данных)** | высокий | дообучение на малом локальном РФ-наборе; база — полный RDD2022, не Japan-only |
| **Drive-by SfM — самый тяжёлый случай** | средне-высокий | DISK+LightGlue; протокол съёмки; отбраковка реконструкций ниже порога inliers/покрытия |
| **Слабый recall заплаток (Repair)** | средний | Repair как best-effort; добить локальной разметкой |
| **Протечки маски SAM на тенях/воде** | средний | оценка/отбраковка качества маски; эскалация на HQ-SAM-base; ограничение road-region маской |
| **Неоднозначность якоря (600 vs 646 мм, категория разметки)** | средний | первичный — лаз 600 мм; пинить издания ГОСТ; ≥2 известных размера для подтверждения |
| **Большие изображения на CPU** | низко-средний | resize длинной стороны до 1024; лимит потоков/RAM; сабсэмплинг тяжёлых датасетов |

**Итог:** CPU/Windows MVP = **детекция + форма (любое фото)** и **метрический размер с эталоном** —
оба на сотнях мс/кадр; **ГОСТ-грейд глубина/объём — только серийный фотограмметрический путь**;
одиночная глубина остаётся явно низкоуверенным несертифицируемым индикатором.

## 11. Стратегия тестирования

- **Юнит-тесты** (без моделей): `shape.py` (дескрипторы на синтетических масках — круг/эллипс →
  известные eq_diameter/eccentricity), `scale.py` (mm/px и гомография на синтетической геометрии),
  `severity.py` (таблица ГОСТ: граничные длина/площадь/глубина → ожидаемые вердикты/сроки),
  `report.py` (валидность JSON-схемы).
- **Интеграционные** (с моделями, медленные, маркер `@pytest.mark.models`): прогон на 6 реальных
  фото — детекция непустая, маски в пределах bbox, JSON валиден, на фото с люком масштаб найден.
- **Валидация качества:** метрики на RDD2022 Czech (mAP детекции) и на seg-наборе (mask IoU);
  «золотая» проверка масштаба — на фото с люком известный лаз 600 мм воспроизводится с ошибкой <15%.
- **Honest-mode тесты:** убедиться, что в Сценарии A/B поле `depth_cm` = null и `depth_certifiable=false`
  (страховка от выдачи несуществующих чисел).
