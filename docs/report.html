Road Defect Engine

CV-движок, который по фотографии дороги находит дефекты, выделяет их контур, при наличии эталона измеряет размеры в сантиметрах и выносит вердикт по ГОСТ — никогда не выдавая чисел, которых физически не может знать.

5 классов дефектов 177 юнит-тестов 3147 строк ядра Python · YOLO · MobileSAM engine v0.1.0

Этот отчёт объясняет проект целиком: что он делает, как устроен и, главное, почему приняты именно такие решения. Читается сверху вниз; технический читатель может прыгать по разделам через оглавление слева.

Суть за 30 секунд

Дан снимок дороги. Нейросеть-детектор находит дефекты (ямы, трещины, заплатки) и их классы. Для каждого дефекта строится точный контур (маска), из контура — форма и размеры в пикселях. Если в кадре есть объект известного размера (канализационный люк), пиксели переводятся в сантиметры. Результат сверяется с ГОСТ Р 50597-2017. Всё, что нельзя измерить честно (в первую очередь — глубина по одному фото), помечается null, а не угадывается. Выход — стабильный JSON и размеченная картинка.

01Задача и контекст

Конечная цель — веб-платформа учёта дорожных дефектов: по фотографиям российских дорог автоматически находить дефекты, определять их форму и размеры, классифицировать серьёзность по ГОСТ Р 50597-2017 и направлять отчёт ответственному за участок. Сегодня этот учёт ведётся вручную: инспектор объезжает дороги, мерит рулеткой, заполняет журнал — медленно, дорого и субъективно.

Система разбита на пять подсистем. Реализована первая — фундамент, к которому остальные подключаются через стабильный контракт:

#ПодсистемаСтатус
1CV-движок: детекция → форма → размеры → серьёзностьготов (MVP)
2Backend API + БД (дефекты, участки, ответственные)позже
3Веб-UI: загрузка фото + карта / дашбордпозже
4Отчёты и уведомления ответственнымпозже
5Геолокация (EXIF GPS + проекция на участок дороги)позже
Почему именно так

Разбиение на подсистемы с общим JSON-контрактом позволяет разрабатывать веб-часть, БД и геолокацию независимо, не трогая и не ломая ядро анализа. Это ключ к тому, чтобы проект рос по частям, а движок оставался стабильным.

02Главный принцип: честность измерений

Архитектура построена вокруг физических ограничений монокулярного (одно-камерного) зрения, а не вопреки им. Это осознанное решение, подтверждённое ресёрчем.

Из одной фотографии разные величины извлекаются с принципиально разной достоверностью:

  • 🟢 Детекция, классификация, форма/контур — решаются на любом RGB-фото.
  • 🟡 Размеры в сантиметрах — только при масштабной привязке: в кадре есть эталон известного размера (люк по ГОСТ 3634, разметка по ГОСТ Р 51256) либо выполнена метрическая 3D-реконструкция.
  • 🔴 Глубина в сантиметрах по одному фото невозможна. 2D-маска и масштаб дают размеры отверстия «в плане», но не вертикаль. Достоверная глубина — только из серии кадров (фотограмметрия / SfM) или датчика.
Следствие для кода

Движок никогда не выдаёт числа, которых физически не может знать. В JSON-отчёте depth_cm всегда null, а depth_certifiable — false, пока нет серии кадров; вердикт ГОСТ без глубины — indeterminate_without_depth, а не угаданное «да/нет». Это защищено специальными honest-mode тестами (tests/test_pipeline_honesty.py) и валидатором отчётов.

Ложный эталон хуже отсутствия эталона

Тот же принцип применён к масштабу. Неверный эталон тихо искажает все сантиметры и вердикты ГОСТ — это опаснее, чем честно не выдать размер. Поэтому каждый кандидат в эталоны проходит многоступенчатое подтверждение, и при сомнении масштаб не выдаётся (см. раздел 4.3).

Каждый модуль отвечает ровно за одну задачу и тестируется изолированно. Модели грузятся лениво и кэшируются между кадрами; интерфейсы абстрактны, поэтому реализацию (ultralytics .pt ↔ ONNX) можно менять без правок конвейера.

Почему детекция идёт до масштаба

Bbox найденных дефектов передаются в поиск эталона и исключаются из кандидатов: круглая тёмная яма или заплатка не должна быть принята за «люк». Порядок стадий — это тоже защита от ложного масштаба.

4.1Детектор дефектов

Решение, принятое с заказчиком: обучение с нуля — нет; дообучение — только как запасной путь на уже размеченных открытых данных. Ориентир железа — CPU-only Windows. Причина: MVP должен заработать быстро и без GPU-инфраструктуры, а для дорожных дефектов есть готовые веса на RDD2022 — крупнейшем открытом датасете повреждений покрытия.

Детектор выбирается из реестра кандидатов — берётся первый загрузившийся:

  1. rezzzq / YOLO12s-RDD2022 — основной. Единственная готовая модель с классом Repair (заплатка); всего 5 классов: D00 продольная трещина, D10 поперечная, D20 сетка, D40 яма, Repair. Обучена на полном RDD2022 (Чехия/Норвегия/США — ближе к РФ, чем Japan-only подмножества). ~100–180 мс/кадр на CPU.
  2. keremberke / YOLOv8m-pothole-seg — одноклассовый, но с instance-масками.
  3. yolo11n-seg (COCO) — технический фолбэк, честно помечается is_fallback=true с предупреждением в отчёте.
Цепочка проверена «в бою»

Из-за бага в имени файла весов первый смок-тест тихо отработал на фолбэк-модели — после фикса реестра основная модель встала на место. Вывод: фолбэк должен быть, но всегда помечен, чтобы «работает» не путалось с «работает правильной моделью».

Слепые пятна детектора и их лечение

На одном демо-фото rezzzq не увидел крупную яму, засыпанную светлым бетоноподобным материалом — ноль детекций даже при пороге conf=0.01 (проверено detect_sweep.py), то есть порогом не лечится. Реализованы два пути:

  • Ансамбль (--ensemble, по умолчанию выкл., ×2 время): второй pothole-проход keremberke, слияние через IoU-дедуп по классу. Та засыпанная яма находится с conf 0.81 и точной маской.
  • Дообучение (finetune_rdd2022.py): от чекпоинта rezzzq с заморозкой слоёв; тренировочный цикл смок-проверен; дообученные веса реестр подхватывает автоматически.
Куда направлять дообучение — вывод валидации

RDD2022 Czech скачан и сконвертирован, mAP-стенд дал mAP50=0.966. Но rezzzq обучалась на полном RDD2022, включая Czech — это train-contaminated число: оно доказывает корректность конвертации и стенда, но не обобщающую способность. Дообучать на Czech бессмысленно (модель его уже видела) — конвейер нацелен на будущую локальную разметку российских фото (см. раздел 7).

4.2Сегментация формы — стратегия по классу

Маска нужна, потому что ГОСТ-метрика (площадь, длина) считается из контура, а не из прямоугольника bbox. Эволюция этого модуля — показательный пример работы принципа честности.

Версия 1 (дизайн): MobileSAM для всех классов

MobileSAM выбран как лучший баланс скорость/качество/размер (40 МБ, Apache-2.0) для CPU: тяжёлый энкодер (~1–4 с) гоняется один раз на кадр (эмбеддинг кэшируется), а декод бокса — десятки миллисекунд.

Поворот: трещины SAM не видит

Визуальная верификация (12 агентов в два раунда сравнивали каждое аннотированное фото с оригиналом) показала: маски ям — отличные, но маски всех трещин негодные — SAM заливал весь bbox или выделял асфальт вокруг. Причина фундаментальна:

Субпиксельность

SAM инференсится на 1024 px, а трещина шириной 1–3 px на смартфонном кадре после даунскейла становится субпиксельной — модель её физически не видит, и никакие промпты это не лечат.

Итог: стратегия по классам

Пороги отбраковки тоже класс-зависимы: линейному дефекту хватает 60 px (трещина 3×60 легальна), площадному нужно 200 px — единый порог 200 терял уверенные детекции трещин целиком.

4.3Масштаб по эталону-люку (ядро честности)

Самый большой модуль проекта (scale.py, 940 строк). Канализационный люк — лучший «бесплатный» эталон на дороге: его размеры нормированы ГОСТ 3634. Из эллипса люка получается изотропный локальный масштаб мм/px.

Мерим 646 мм, а не 600

На дороге люк почти всегда ЗАКРЫТ, и контурный детектор видит наружный обод крышки ≈646 мм, а не лаз 600 мм (лаз виден только у открытого колодца). Первая версия кода мерила обод, а считала его лазом — систематическое занижение ~7%. Якорь по умолчанию — обод 646 мм.

Почему только локальный масштаб, а не полная гомография

Полная гомография по одному кругу без фокусного расстояния камеры не определяется (8 степеней свободы гомографии против 5 у эллипса). Поэтому по люку выдаётся локальный масштаб с полосой ошибки ±10–30% по наклону; полная гомография строится только при 4 известных копланарных точках.

Защита от ложного эталона — хронология находок

Это центральная тема модуля. Каждый пункт — реальный баг, пойманный диагностикой или визуальной проверкой и закрытый:

  1. Подтверждение эллипсом. Кандидат-круг Hough подтверждается подгонкой эллипса по контуру (центр и диаметр согласованы), иначе масштаб не выдаётся.
  2. «Крупнейший круг = люк». Hough на текстуре асфальта галлюцинирует гигантские круги (r≈400+ px), и эвристика выбирала их — настоящий люк даже не проверялся. Исправлено: кандидаты перебираются в порядке силы отклика до первого подтверждённого.
  3. Выбор контура. Подгонка эллипса брала первый контур больше порога, а порядок контуров произволен — эллипс мог сесть на тень рядом. Исправлено: берётся контур, чей эллипс ближе к кандидату.
  4. Косой ракурс. На смартфонных снимках люк сплюснут перспективой в эллипс 2:1+, и HoughCircles его не находит. Добавлен второй путь — прямой поиск тёмных эллиптических блобов с шестью фильтрами (размер, целиком в кадре, аспект ≥0.45, заполненность, контраст с кольцом, опора на кромки Canny).
  5. Блоб-путь выключен по умолчанию. На реальном фото тень под бордюрным камнем прошла все шесть фильтров и стала «люком» с наклоном 74.5° — поймано визуальной проверкой кропа. Вывод: до «золотой» валидации автоматический блоб-якорь слишком рискован (--blob-ref включает его явно).
  6. Гейт дорожной плоскости. Круглый эллипс высоко в кадре — это вертикальная поверхность (баннер/знак), давшая ложный масштаб. Люк — горизонтальный диск в нижней части кадра; далёкий люк у горизонта сильно сплюснут. Поэтому отклоняется кандидат «высоко И слишком круглый».
  7. Исключение зон детекций. Кандидат с центром внутри найденного дефекта эталоном не становится.
Текущая честная граница

Серые чугунные крышки на сером асфальте порог по тёмному не выделяет — масштаб на них недоступен. Это типичная ситуация «лучше нет числа, чем неверное число»; системное решение — отдельный класс «люк» в детекторе (будущий цикл).

Мульти-эталон с кросс-валидацией

Кроме люка, поддержаны разметка (ГОСТ Р 51256, ширина штриха) и борт (ГОСТ 6665, грань 150 мм) — оба выключены по умолчанию. Причина — адверсариальное ревью: класс ширины разметки по одному штриху неоднозначен (линия 1.1 = 80–150 мм vs краевая = 100–200 мм vs СТОП-линия = 400 мм), а ориентация в кадре не отличает поперечную линию от ракурсно-«горизонтальной» продольной — это даёт ложный масштаб 2.5–5×. Поэтому разметка требует положительного признака краски (тёмный асфальт по обе стороны штриха), выдаётся только как low-confidence и повышается лишь при кросс-подтверждении люком. При конфликте разнотипных эталонов уверенность «липко» падает до low, полоса расширяется, в отчёт пишется «конфликт эталонов» — конфликтующие эталоны никогда не усредняются молча.

4.4Слияние двух видов одной ямы

Основной практический сценарий текущей версии: яму снимают двумя кадрами — front.jpg «впереди» и back.jpg «позади» — и все пары обрабатываются одной командой. Реализация честна в рамках физики двух встречно-косых кадров (это не полноценная фотограмметрия).

  • Геометрия. Встречно-косые виды укорачивают план по закону cos(наклон) синфазно — простое усреднение смещение не убирает. Поэтому площадь корректируется за наклон (area/cos) и сливается обратно-дисперсионно — но только когда наклон известен в обоих видах (по люку). Длина/ширина не корректируются (нет азимута наклона) и берутся как нижняя оценка — максимум сырых значений (ракурс только укорачивает), чтобы не занизить ногу ГОСТ «длина ≥ 15 см».
  • Главный выигрыш — уверенность, не полоса. Согласие видов повышает уверенность на ступень, но только если оно независимо (хотя бы один вид с известным наклоном). Полоса ошибки никогда не уже худшего одиночного вида.
  • Честность. Глубину в см слияние не выдаёт никогда. Без масштаба хотя бы в одном виде или при невозможности сопоставить одну доминирующую яму — режим two_view_unmatched, показываются одиночные результаты, фабрикованных см нет. Сильно разная форма видов → вероятно, это разные ямы → слияние не выполняется.

4.5Глубина — только относительный бакет

depth.py использует Depth Anything V2 Small (важно: только Small — Apache-2.0; Base/Large под CC-BY-NC и в продукт нельзя). Модуль никогда не выдаёт сантиметры — только категорию shallow / medium / deep.

Кольцевая плоскостная линейка

К кольцу вокруг маски робастно подгоняется плоскость дороги. Числитель — медианная просадка ядра маски под плоскостью. Знаменатель — перепад этой плоскости на поперечной (перпендикулярной градиенту) ширине маски. Поперечная ширина не сжимается ракурсом, поэтому индикатор rel_norm ≈ глубина/ширина инвариантен к дистанции, зуму и высоте камеры.

Что поймало ревью

Первая версия линейки нормировала на кругово-эквивалентный диаметр, и индикатор рос как √дистанции — заменено на поперечную ширину. Съёмка «в надир», крошечная маска, отсутствие кольца или просадка ниже 3σ шума → честный отказ (bucket = null). Калибровка на 14 демо-дефектах положительного сигнала не выявила: DA-V2-Small на этих ямах рельефа не кодирует — это правильный «shallow» по правильной причине. ГОСТ-глубина ≥5 см появится только со Сценарием C (фотограмметрия: COLMAP + hloc + OpenMVS, отложен по дизайну).

4.6Серьёзность по ГОСТ Р 50597-2017

Одиночный дефект не соответствует норме, когда выполнены ВСЕ ТРИ условия (п. 5.2.4 действующего ГОСТ, а не легаси «15×60×5» из редакции-93):

≥ 15
см — длина
≥ 5
см — глубина
≥ 0.06
м² — площадь

Поскольку глубина в сценариях A/B не сертифицируема, движок честно проверяет две ноги из трёх и выдаёт non_conforming: indeterminate_without_depth с пояснением. Сроки устранения по категории дороги (IA: 1 сутки … V: 12 суток) и требование обозначить опасный участок за 2 часа зашиты в config.py и появляются в отчёте только когда вердикт определён. Все числовые константы ГОСТ живут только в config — дублирование по коду запрещено.

4.7Семантика метрики: что такое «длина» и «площадь»

Решение принято по итогам адверсариального ревью, находка подтверждена с численным воспроизведением:

  • length_cm / width_cm — физическая протяжённость: стороны минимального повёрнутого прямоугольника (cv2.minAreaRect). Раньше длиной была ось эллипса инерции — для равномерной полосы это +15.5% систематически: прямая трещина истинной длиной 13.2 см репортилась как 15.2 см и ложно включала ногу ГОСТ «длина ≥ 15 см».
  • area — суммарная площадь всех компонент маски, совпадает с mask_rle. Раньше считалась только крупнейшая компонента — фрагментированная маска трещины теряла площадь в разы.
  • Дескрипторы формы (eccentricity, solidity, ориентация) считаются по крупнейшей компоненте — это характеристики формы, а не размера.

05JSON-контракт — стабильный выход движка

Выход движка стабилен и потребляется будущими подсистемами 2–5: блок scale с эталоном, по каждому дефекту — класс, confidence, bbox, mask_rle (COCO-стиль), дескрипторы формы, блок metric (всегда полный набор ключей, null где измерить нельзя), severity и warnings человеческим языком. Ниже — реальный фрагмент для фото без эталона (яма + продольная трещина):

// эталона в кадре нет → scale.available=false
{
  "class": "pothole", "confidence": 0.805,
  "mask_method": "mobile_sam_ultralytics",
  "shape": { "length_px": 139.5,
             "eccentricity": 0.87,
             "solidity": 0.97 },
  "metric": { "available": false,
              "length_cm": null,
              "depth_cm": null,
              "depth_certifiable": false },
  "severity": {
    "standard": "ГОСТ Р 50597-2017",
    "non_conforming": "indeterminate_without_depth",
    "note": "Глубину нельзя подтвердить по этому
             входу — нужна серийная съёмка.
             размеры не измерены (нет эталона)." }
}

Обратите внимание: форма посчитана в пикселях (её можно), а все сантиметры и вердикт — честно null / indeterminate. Соблюдение контракта проверяется тестами и validate_outputs.py на каждом прогоне.

06Окружение, устойчивость и лицензии

  • Кириллические пути Windows. cv2.imread/imwrite молча не работают с русскими путями — чтение/запись идёт через np.fromfile + imdecode / imencode + tofile, запись проверяется.
  • Консоль cp1251. Перенаправленный stdout на русской Windows кодируется cp1251, и символ вне неё (например, «→») ронял CLI — потоки переведены в errors="replace".
  • Бюджет CPU. Тяжёлые полнокадровые операции (эмбеддинг SAM, карта глубины) выполняются один раз на кадр и кэшируются по md5 содержимого; GrabCut строит граф по кропу вокруг bbox, а не по всему 12-МП кадру.
  • Прозрачность отказов. Детекция, отброшенная из-за негодной маски, оставляет warning в отчёте, а не исчезает молча; неизвестная категория дороги отклоняется CLI на входе.
Лицензии — с прицелом на распространение

ultralytics — AGPL-3.0: для распространяемого продукта инференс надо перевести на ONNX без импорта ultralytics в рантайме (запланировано). MobileSAM и Depth Anything V2 Small — Apache-2.0 (чисто). Датасет RDD2022 — CC BY-SA 4.0. Сознательно не используются EdgeSAM, SuperPoint/SuperGlue, Depth Anything Base/Large (все некоммерческие).

08Как проверяется качество

Четыре независимых, воспроизводимых уровня:

  1. Юнит-тесты (177 шт., pytest -q, без сети и моделей): дескрипторы формы на синтетике с известными ответами (включая регрессию «+15.5% длины»), таблица ГОСТ на граничных значениях, масштаб (Hough на синтетическом кадре, наклонный люк, отбой теней/пятен/ обрезанных эллипсов), маршрутизация сегментатора, honest-mode инварианты, юникод-I/O, RLE.
  2. Смок-тест на реальных фото (smoke_test.py): какие модели загрузились, сколько дефектов, какие методы масок; затем validate_outputs.py проверяет инварианты всех JSON.
  3. Визуальная верификация агентами: агент на каждое фото сравнивает оригинал / разметку / JSON и выдаёт структурированный вердикт по каждой маске. Именно этот механизм поймал оба ложных эталона и негодные маски трещин.
  4. Демо-отчёт (make_demo_report.py): человекочитаемый разрез тех же результатов; рендер проверяется скриншотами.
Что валидировано, а что ещё нет

Сделано: mAP-стенд на RDD2022 Czech (с честной оговоркой про train-contamination). Ещё не сделано: «золотая» проверка масштаба (ошибка <15% на фото с известным люком) и mask IoU на сегментационном наборе — честно указаны как открытые пункты.

09Метод разработки

Проект развивается циклами. Каждый цикл: спека (что и почему) → реализация модуля с тестами → адверсариальное ревью (агенты-скептики ищут и воспроизводят дефекты) → фикс подтверждённых находок → коммит с записью в журнал docs/STATUS.md.

Многие ключевые улучшения — прямой результат этого ревью, а не первоначального замысла:

  • ложный масштаб 2.5–5× по ориентации штриха разметки → разметка/борт off по умолчанию;
  • seg-маски YOLO читались в letterbox-координатах (critical) → исправлено;
  • +15.5% к длине из-за оси эллипса → физическая протяжённость minAreaRect;
  • √-зависимость индикатора глубины от дистанции → нормировка на поперечную ширину;
  • тень под бордюром как «люк» → блоб-путь выключен по умолчанию.
Почему это важно для доверия

Каждое инженерное решение записано вместе с обоснованием «почему» и датой. Это делает проект проверяемым: любое число (646 мм, 15 см, 0.45 аспект) можно проследить до источника — ГОСТ, ресёрч или конкретная находка ревью.

10Запуск

# проверка: тесты, смок, инварианты
python -m pytest -q
python scripts/smoke_test.py
python scripts/validate_outputs.py

# боевой запуск: папка фото → outputs/*.json + *_annotated.jpg
$env:PYTHONPATH="src"
python -m road_defect.cli --input <папка> --output outputs
#   --depth      относительная глубина (нужен transformers)
#   --ensemble   второй pothole-проход (нетипичные ямы, x2 время)
#   --road-category IV   категория дороги для сроков ГОСТ

# слияние двух видов одной ямы
python -m road_defect.cli --pair front.jpg back.jpg --output outputs

# пакет пар + сводная таблица
python -m road_defect.cli --pairs-dir datasets/local_pairs --output outputs_pairs

Веса моделей докачиваются автоматически при первом запуске (детектор с HF Hub, mobile_sam.pt с CDN ultralytics, Depth Anything — в кэш HF).
