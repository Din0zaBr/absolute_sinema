# Работа с сериями из двух фото

Цель текущего этапа: научить проект принимать много комплектов вида "один дефект = два фото" и честно определять дефект только по изображениям. Для каждого дефекта нужны два кадра: вид спереди и вид сзади.

## Что уже сделано

- В движке уже есть анализ одной пары через `DefectPipeline.analyze_pair(front, back)`.
- В командной строке есть режим `--pair FRONT.jpg BACK.jpg` для одного дефекта.
- Добавлен массовый режим `--pairs-dir`, который обрабатывает сразу папку с несколькими дефектами.
- Для каждой пары сохраняются JSON-отчет, аннотированная картинка и общая таблица `pairs_summary.csv`.
- В JSON добавляются `pair_id` и `pair_inputs`, чтобы было понятно, из какой подпапки и каких двух файлов получен результат.
- Добавлены тесты на поиск пар, сохранение отчетов и защиту от перезаписи файлов `front/back` из разных подпапок.

## Как подготовить фото

Структура папки должна быть такой:

```text
datasets/local_pairs/
  001/
    front.jpg
    back.jpg
  002/
    front.jpg
    back.jpg
  003/
    front.jpg
    back.jpg
```

Допустимые имена для переднего вида: `front`, `before`, `a`, `1`, `view_a`.
Допустимые имена для заднего вида: `back`, `after`, `b`, `2`, `view_b`.

Лучше использовать именно `front.jpg` и `back.jpg`: так меньше риска перепутать направление.

## Как запускать

```powershell
$env:PYTHONPATH="src"; python -m road_defect.cli --pairs-dir datasets/local_pairs --output outputs_pairs
```

После запуска смотри:

- `outputs_pairs/*.json` - подробные машинные отчеты;
- `outputs_pairs/*_annotated.jpg` - картинки с найденными дефектами;
- `outputs_pairs/pairs_summary.csv` - короткая таблица по всем парам.

## Что можно сделать прямо сейчас

1. Собрать первые 20-30 пар фото одного типа дефекта, например только ямы.
2. Для каждой пары вручную записать, есть ли дефект на самом деле: `yes/no`.
3. Запустить `--pairs-dir` и открыть `pairs_summary.csv`.
4. Разделить ошибки на три группы: дефект пропущен, найден лишний объект, найден не тот контур.
5. Добавить 5-10 самых плохих примеров в отдельную папку `datasets/local_pairs_hard`.
6. После этого решать, нужно ли дообучение модели или достаточно настроить порог `--conf` и включить `--ensemble`.

## Как понять качество

Минимальная ручная проверка для текущего этапа:

| Метрика | Что означает | Цель для первого рабочего прототипа |
|---|---|---|
| Recall | сколько настоящих дефектов найдено | не ниже 80% на своих фото |
| False positives | сколько лишних дефектов найдено | не больше 1-2 на 10 пар |
| Контур | насколько маска похожа на реальную форму | визуально приемлемо для отчета |
| Стабильность пары | один и тот же дефект найден на двух видах | большинство хороших пар |

Формально для первой проверки достаточно таблицы:

```text
recall = найденные_реальные_дефекты / все_реальные_дефекты
precision = найденные_реальные_дефекты / все_найденные_дефекты
```

Таблицу и сводку строит `scripts/pair_quality_table.py` (совмещает
JSON-отчёты `--pairs-dir` с журналом сбора). Три тонкости, чтобы не
обмануться числами:

- «Яма найдена в виде» = детектор выдал хотя бы одну pothole-детекцию
  (`select_status != no_pothole`). Поле `pothole_found` из JSON — про другое:
  выбрана ли ОДНА доминирующая яма для слияния видов; при нескольких близких
  ямах оно честно `false`, и как мера recall оно занижает.
- Recall считается и по парам, и по сценам: соседние ямы сборщик снимает
  одним общим кадром, пары одной сцены — одни и те же файлы (колонка `scene`
  журнала, её пишет `scripts/ingest_local_pairs.py`).
- `matched_rate` — доля пар, где виды сопоставлены (это и есть «стабильность
  пары»); `fused_rate` требует масштаба (эталона в кадре) в ОБОИХ видах —
  без люка/разметки в кадре он честно 0%, это не поломка слияния.

## Честное ограничение двух фото

По двум фото можно качественно обнаруживать дефект и повышать уверенность, если дефект виден с двух сторон. Но два обычных косых кадра не дают надежную глубину в сантиметрах. Для глубины нужна серия кадров с перекрытием, фотограмметрия, LiDAR или физический эталон в кадре.

Текущий проект поэтому не выдумывает глубину: если данных недостаточно, в отчете остается честный режим `two_view_unmatched` или размер без сертифицируемой глубины.

## Следующие цели проекта

1. Стабилизировать сбор данных: 20-30 пар фото одного дефекта по одному протоколу съемки.
2. Получить первую локальную таблицу качества: сколько дефектов найдено, сколько пропущено.
3. Подобрать рабочий режим запуска: обычный детектор, `--ensemble`, порог `--conf`.
4. Если ошибок много, подготовить локальный набор для дообучения.
5. После обнаружения перейти к серии кадров для глубины и объема, если это потребуется для ГОСТ-оценки.
