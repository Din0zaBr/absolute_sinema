**Обновлено:** 2026-06-12

## 1. Что это и зачем

Конечная цель — **веб-платформа учёта дорожных дефектов**: по фотографиям
российских дорог автоматически находить дефекты (ямы, трещины, заделки),
определять их форму и размеры, классифицировать серьёзность по
**ГОСТ Р 50597-2017** и направлять отчёт ответственному за участок.

Система декомпозирована на 5 подсистем; реализована первая — фундамент:

| # | Подсистема | Статус |
|---|-----------|--------|
| **1** | **CV-движок**: детекция → форма → размеры → серьёзность | **готов (MVP)** |
| 2 | Backend API + БД (дефекты, участки, ответственные) | позже |
| 3 | Веб-UI: загрузка фото + карта/дашборд | позже |
| 4 | Отчёты/уведомления ответственным | позже |
| 5 | Геолокация (EXIF GPS + проекция на участок дороги) | позже |

Подсистемы 2–5 подключаются к движку через **стабильный JSON-контракт**
(раздел 6) — это позволяет разрабатывать их независимо.

## 2. Главный принцип: честность измерений

Архитектура построена вокруг физических ограничений монокулярного зрения,
а не вопреки им. Это решение брейншторма с заказчиком, подтверждённое ресёрчем:

1. 🟢 **Детекция, классификация, форма/контур** — решаются на любом RGB-фото.
2. 🟡 **Размеры в сантиметрах** — только при **масштабной привязке**: в кадре
   есть эталон известного размера (канализационный люк по ГОСТ 3634, дорожная
   разметка по ГОСТ Р 51256) либо выполнена метрическая 3D-реконструкция.
3. 🔴 **Глубина в сантиметрах по одному фото невозможна.** 2D-маска + масштаб
   дают размеры отверстия в плане, но не вертикаль. Достоверная глубина —
   только из серии кадров (фотограмметрия/SfM, «Сценарий C») или датчика.

**Следствие:** движок никогда не выдаёт числа, которых физически не может
знать. В JSON-отчёте `depth_cm` всегда `null`, `depth_certifiable` всегда
`false`, пока нет Сценария C; вердикт ГОСТ без глубины —
`indeterminate_without_depth`, а не угаданное «да/нет». Это защищено
специальными honest-mode тестами (`tests/test_pipeline_honesty.py`) и
валидатором отчётов (`scripts/validate_outputs.py`).

Тот же принцип применён к масштабу: **ложный эталон хуже отсутствия эталона**,
потому что тихо искажает все сантиметры и вердикты ГОСТ. Поэтому каждый
кандидат в эталоны проходит многоступенчатое подтверждение, и при сомнении
масштаб честно не выдаётся (подробно — раздел 4.4).

### Три сценария работы

| Величина | A: фото без эталона | B: фото с эталоном | C: серия кадров (план) |
|----------|--------------------|--------------------|------------------------|
| Форма (eccentricity, solidity) | ✅ | ✅ | ✅ |
| Диаметр/длина/площадь, см | ❌ (только px) | ✅ ±10–20% | ✅ |
| Глубина, см | ❌ (только бакет) | ❌ (только бакет) | ✅ ГОСТ-грейд |

## 3. Архитектура

Каждый модуль — одна ответственность, тестируется изолированно:

```
src/road_defect/
  config.py     # единая точка правды: ГОСТ-константы, классы, реестр моделей, пороги
  pipeline.py   # оркестратор: фото -> JSON-отчёт + аннотированное изображение
  detect.py     # детектор дефектов (YOLO, авто-выбор работающих весов)
  segment.py    # маска формы: класс-зависимая стратегия (см. 4.3)
  shape.py      # дескрипторы формы из маски (skimage.regionprops)
  scale.py      # масштаб по эталону-люку + гомография (см. 4.4)
  depth.py      # относительная глубина: бакет shallow|medium|deep (см. 4.5)
  severity.py   # вердикт по ГОСТ Р 50597-2017 (см. 4.6)
  report.py     # JSON-контракт §8 + overlay; RLE-кодирование масок
  imgio.py      # чтение/запись изображений (кириллические пути Windows)
  cli.py        # командная строка
scripts/
  smoke_test.py        # прогон на демо-фото с диагностикой окружения
  validate_outputs.py  # проверка инвариантов JSON-отчётов
  detect_sweep.py      # все сырые детекции при минимальном пороге (разбор пропусков)
  scale_debug.py       # постадийная диагностика эталона-люка
```

**Поток данных одного фото:**

```
image → detect (YOLO)
      → scale (эталон-люк; bbox'ы детекций исключены из кандидатов)
      → для каждого дефекта: segment → shape → metric (если есть масштаб)
      → depth (опционально, --depth)
      → severity (ГОСТ)
      → report (JSON + overlay)
```

Детекция идёт **до** масштаба не случайно: bbox'ы найденных дефектов
исключаются из кандидатов в эталоны, чтобы круглая тёмная яма или заплатка
не стала «люком» (см. 4.4).

Модели грузятся лениво и кэшируются между кадрами. Интерфейсы абстрактны:
реализацию (ultralytics `.pt` ↔ ONNX) можно менять без правок конвейера.

## 4. Ключевые решения и их обоснования

### 4.1. Только готовые предобученные модели

**Решение** (с заказчиком): обучение с нуля — нет; дообучение — только как
запасной путь, на уже размеченных открытых данных. Ориентир железа —
**CPU-only Windows**.

**Почему:** MVP должен заработать быстро и без GPU-инфраструктуры; для
дорожных дефектов существуют готовые веса на RDD2022 — крупнейшем открытом
датасете дорожных повреждений.

### 4.2. Детектор: rezzzq/yolo12s-rdd2022 + фолбэк-цепочка

**Решение:** реестр кандидатов в `config.DETECTOR_CANDIDATES`, берётся первый
загрузившийся:
1. `rezzzq/yolo12s-road-damage-rdd2022` (HF) — **основной**;
2. `keremberke/yolov8m-pothole-segmentation` — одноклассовый, но с instance-масками;
3. `yolo11n-seg` (COCO) — технический фолбэк, честно помечается
   `is_fallback=True` с предупреждением в отчёте.

**Почему rezzzq:** единственная готовая модель с классом **Repair/заплатка**
(всего 5 классов: D00 продольная трещина, D10 поперечная, D20 сетка, D40 яма,
Repair), обучена на полном RDD2022 (Чехия/Норвегия/США — ближайший прокси к
РФ, а не Japan-only подмножества). ~100–180 мс/кадр на CPU.

**Почему цепочка:** загрузка весов из сети может падать; конвейер должен
оставаться работоспособным и при этом не врать (фолбэк всегда помечен).
Цепочка проверена в бою: из-за бага имени файла весов (`best.pt` вместо
`yolo12s_RDD2022_best.pt`) первый смок-тест тихо отработал на keremberke —
после фикса реестра основная модель встала на место.

**Известное ограничение:** на одном демо-фото (`6dyN…`) rezzzq не видит
крупную яму, засыпанную светлым бетоноподобным материалом, — **ни одной
детекции даже при conf=0.01** (проверено `detect_sweep.py`), т.е. порогом не
лечится. Одноклассовый keremberke видел её с conf=0.81. Решение — за
заказчиком: опциональный второй pothole-проход (ансамбль — отступление от
принципа «один выбор на роль») или дообучение на RDD2022 (предусмотренный
запасной путь).

### 4.3. Сегментация формы: класс-зависимая стратегия

Маска нужна, потому что ГОСТ-метрика (площадь, длина) считается из контура,
а не из bbox. Эволюция решения — хороший пример работы принципа честности:

**Версия 1 (дизайн):** MobileSAM по bbox-промпту для всех классов.
MobileSAM выбран как лучший баланс скорость/качество/размер (40 МБ,
Apache-2.0) для CPU: энкодер ~1–4 с/кадр гоняется **один раз на кадр**
(эмбеддинг кэшируется), декод бокса — десятки миллисекунд.

**Поворот 1: установка.** `pip install git+…MobileSAM` оказался недоступен
(политика безопасности — внешний код из GitHub). Вместо этого используется
**встроенная реализация `ultralytics.models.sam`** — это тот же MobileSAM
(vit_t), новых пакетов не нужно, веса `mobile_sam.pt` докачиваются с CDN
ultralytics тем же механизмом, что YOLO-веса. Если официальный пакет
`mobile_sam` всё же установлен — он используется первым (цепочка бэкендов:
пакет → ultralytics → GrabCut).

**Поворот 2: трещины.** Визуальная верификация (12 агентов в два раунда,
смотрели каждое аннотированное фото против оригинала) показала: маски ям —
отличные, но **маски всех трещин — негодные**: SAM заливал bbox целиком или
выделял асфальт вокруг трещины. Причина фундаментальна: SAM инференсится на
1024px, а трещина шириной 1–3 px на смартфонном кадре после даунскейла
становится **субпиксельной** — модель её физически не видит, и никакие
промпты это не лечат.

**Итоговое решение — стратегия по классам** (`segment.py`):

| Класс дефекта | Метод | Почему |
|---------------|-------|--------|
| Линейные: `longitudinal_crack`, `transverse_crack` | классика в **полном разрешении** внутри bbox: black-hat (тёмная трещина) → top-hat (трещина, забитая светлой пылью) → Otsu → фильтры площади и **вытянутости** компонент | морфология с ядром шире трещины откликается ровно на тонких линиях; полное разрешение сохраняет субпиксельные для SAM структуры; трещина вытянута, а текстурный шум и пятна тени округлы |
| Площадные: `pothole`, `patch`, `alligator_crack` | MobileSAM по bbox | подтверждено верификацией: маски «good», плотно по контуру |
| Любой класс, если выше не сработало | GrabCut внутри bbox | конвейер всегда даёт контур; метод честно записывается |

Каждый дефект в JSON несёт поле **`mask_method`**
(`detector_mask | crack_blackhat | crack_tophat | mobile_sam[_ultralytics] |
grabcut`) — потребитель и контролёр качества видят происхождение каждой маски.

Пороги отбраковки тоже класс-зависимы: линейному дефекту 60 px достаточно
(трещина 3×60 px легальна), площадному нужно 200 px. Единый порог 200 терял
уверенные детекции трещин целиком. Если крэк-экстрактор дал слишком мало
пикселей, сегментатор сам уходит в SAM — деградирует качество маски, но
детекция не пропадает из отчёта.

**Результат повторной верификации:** тёмные трещины «poor → acceptable»
(узкая лента вдоль трещины вместо заливки). **Известные ограничения** (лечатся
только специализированной crack-seg моделью, например дообучением на
CrackSeg9k/SegmRDD): крупные пятна тени дают дугообразные — тоже вытянутые —
отклики по границе и могут просачиваться в маску; часть светлых трещин не
проходит фильтры правдоподобия и честно падает в SAM-заливку.

### 4.4. Масштаб: эталон-люк по ГОСТ 3634

**Базовое решение:** канализационный люк — лучший «бесплатный» эталон на
дороге, его размеры нормированы ГОСТ 3634. Из эллипса люка получается
изотропный локальный масштаб `mm/px`; полная гомография по одному кругу без
фокусного расстояния **не определяется** (8 степеней свободы гомографии
против 5 у эллипса) — поэтому гомография строится только при 4 известных
копланарных точках (`homography_from_4_points`), а по люку выдаётся локальный
масштаб с полосой ошибки ±10–30% в зависимости от наклона.

**Какой размер мерить — 646, а не 600 мм.** На дороге люк почти всегда
ЗАКРЫТ, и контурный детектор видит **наружный обод крышки ≈646 мм**, а не лаз
600 мм (лаз виден только у открытого колодца). Первая версия кода мерила обод,
а считала его лазом — систематическое занижение ~7%. Якорь по умолчанию —
`manhole_gost3634_cover` (646 мм); 600 мм передаётся явно для открытого проёма.

**Защита от ложного эталона** — центральная тема этого модуля. Хронология:

1. **Подтверждение эллипсом:** кандидат-круг Hough подтверждается подгонкой
   эллипса по контуру (центр и диаметр согласованы), иначе масштаб не выдаётся.
2. **Баг «крупнейший круг = люк»:** постадийная диагностика
   (`scale_debug.py`) на реальных фото показала, что Hough на текстуре асфальта
   галлюцинирует гигантские круги (r≈400+ px), эвристика выбирала их, и
   настоящий люк даже не проверялся. Исправлено: кандидаты перебираются
   **в порядке силы отклика аккумулятора** до первого подтверждённого.
3. **Баг выбора контура:** `fit_manhole_ellipse` брал первый контур больше
   порога площади, а порядок `findContours` произволен — эллипс мог сесть на
   тень рядом. Исправлено: берётся контур, чей эллипс ближе всего к кандидату.
4. **Фундаментальное ограничение Hough:** на косых смартфонных снимках люк
   сплюснут перспективой в эллипс 2:1+, и HoughCircles (ищет почти-круги) не
   находит его в принципе. Добавлен второй путь — **поиск тёмных эллиптических
   блобов** напрямую (порог тёмного → контуры → fitEllipse) с шестью фильтрами:
   размер ≥8% короткой стороны кадра, эллипс целиком в кадре, аспект ≥0.45
   (наклон >63° бессмыслен для изотропного масштаба, и это профиль теней),
   заполненность контуром 0.75–1.25 площади эллипса, контраст с окружающим
   кольцом, опора ≥50% периметра на кромки Canny.
5. **Блоб-путь выключен по умолчанию.** На реальном фото первая версия
   фильтров пропустила обрезанное кадром пятно 83 px, ужесточённая — **тень под
   бордюрным камнем** (прошла ВСЕ шесть фильтров и стала «люком» с наклоном
   74.5°); поймано визуальной проверкой кропа. Вывод: до «золотой» валидации
   масштаба (известный люк воспроизводится с ошибкой <15%) автоматический
   блоб-якорь слишком рискован. Путь включается явно: флаг CLI `--blob-ref`
   или `InferenceConfig.allow_blob_reference=True`.
6. **Исключение зон детекций:** конвейер передаёт bbox'ы найденных дефектов,
   и кандидат с центром внутри детекции эталоном не становится (круглая тёмная
   яма не станет «люком»).

**Текущая честная граница:** серые чугунные крышки на сером асфальте (все три
демо-фото с люками) порог по тёмному не выделяет — масштаб на них недоступен.
Системное решение — отдельный класс «люк» в детекторе (будущий цикл); это
типичная ситуация «лучше нет числа, чем неверное число».

**Вторичный эталон по дизайну** — ширина дорожной разметки (ГОСТ Р 51256-2018:
линия 1.1 = 100 мм, СТОП-линия = 400 мм); в коде пока только константы.

### 4.5. Глубина: только относительный бакет

`depth.py` использует Depth Anything V2 **Small** (важно: только Small —
Apache-2.0; Base/Large под CC-BY-NC и в продукт нельзя) через `transformers`.

Модуль **никогда не выдаёт сантиметры**. Сравнивается медианная относительная
глубина внутри маски дефекта и в «кольце» вокруг него; результат — бакет
`shallow|medium|deep` для приоритезации + имя метода. Это опциональный флаг
`--depth`; без установленного `transformers` модуль молча превращается в no-op.

ГОСТ-сертифицируемая глубина ≥5 см появится только со Сценарием C
(`photogrammetry.py`): COLMAP CPU sparse SfM + hloc (DISK+LightGlue — именно
они, потому что SuperPoint/SuperGlue non-commercial) + OpenMVS CPU dense
(dense-реконструкция COLMAP/Meshroom требует CUDA). Отложен по дизайну.

### 4.6. Серьёзность по ГОСТ Р 50597-2017

Одиночный дефект **не соответствует норме**, когда выполнены ВСЕ ТРИ условия
(п. 5.2.4 действующего ГОСТ, а не легаси «15×60×5» из редакции-93):
длина ≥ 15 см **И** глубина ≥ 5 см **И** площадь ≥ 0.06 м².

Поскольку глубина в Сценариях A/B не сертифицируема, движок честно проверяет
две ноги из трёх и выдаёт `non_conforming: indeterminate_without_depth` с
пояснением. Сроки устранения по категории дороги (IA: 1 сутки … V: 12 суток,
табл. 5.3) и требование обозначить опасный участок за 2 часа (п. 4.4 ГОСТ)
зашиты в `config.py` и появляются в отчёте только когда вердикт определён.

Все числовые константы ГОСТ живут **только** в `config.py` (единая точка
правды) — дублирование по коду запрещено.

### 4.7. JSON-контракт (§8 дизайна)

Выход движка стабилен и потребляется будущими подсистемами 2–5: блок `scale`
с вложенным `reference` (тип якоря, известный размер, измеренные px),
`homography_applied`, по каждому дефекту — класс, confidence, bbox,
`mask_rle` (COCO-стиль, column-major, размер равен кадру), дескрипторы формы,
блок `metric` (всегда полный набор ключей, `null` где измерить нельзя),
`severity`, плюс `warnings` человеческим языком. Соблюдение контракта
проверяется тестами и `validate_outputs.py` на каждом прогоне.

### 4.8. Окружение и I/O

- **`imgio.py`:** `cv2.imread/imwrite` на Windows молча не работают с
  кириллическими путями — чтение/запись идёт через
  `np.fromfile`+`imdecode` / `imencode`+`tofile`, запись проверяется.
- **CLI и cp1251:** перенаправленный stdout на русской Windows кодируется
  cp1251, и символ вне неё (например, `→`) ронял CLI с UnicodeEncodeError.
  Потоки переводятся в `errors="replace"`. (Смок-тест не падал случайно:
  `import ultralytics` успевал перенастроить консоль.)
- **Имена результатов:** уникализируются в рамках прогона (`unique_stem`),
  иначе смартфонные серии `IMG_2026…` перезаписывали отчёты друг друга.
- **SAM-предиктор ultralytics** создаётся с `save=False`, иначе он молча
  пишет собственные overlay в `runs/` на каждый кадр.

### 4.9. Лицензии (для будущего распространения)

- `ultralytics` — **AGPL-3.0**: для распространяемого продукта инференс надо
  перевести на ONNX (`onnxruntime`) без импорта `ultralytics` в рантайме,
  либо принять AGPL/купить Enterprise. Это запланированный шаг (план, п. 5).
- MobileSAM, Depth Anything V2 **Small** — Apache-2.0 (чисто).
- Лицензионный тег весов rezzzq — открытый вопрос перед коммерческим релизом.
- Избегаются: EdgeSAM (non-commercial), SuperPoint/SuperGlue (non-commercial),
  Depth Anything Base/Large (CC-BY-NC), Marigold (минуты/кадр).

## 5. Как проверяется качество

Три уровня, все воспроизводимы:

1. **Юнит-тесты, 43 шт.** (`pytest -q`, без сети и моделей): дескрипторы формы
   на синтетике с известными ответами; таблица ГОСТ на граничных значениях;
   масштаб (Hough на синтетическом 12-МП кадре, наклонный люк через блоб-путь,
   отбой теней/пятен/обрезанных эллипсов, исключение bbox); крэк-экстрактор
   (тёмная/светлая линия, отбой округлых пятен); маршрутизация сегментатора
   (предиктор замокан); honest-mode инварианты; юникод-I/O; RLE.
2. **Смок-тест на 6 реальных фото** (`scripts/smoke_test.py`): какие модели
   загрузились, сколько дефектов, какие методы масок; затем
   `scripts/validate_outputs.py` проверяет инварианты всех JSON. Текущий
   результат: 14 дефектов, без падений, инварианты соблюдены.
3. **Визуальная верификация агентами** (воркфлоу: агент на фото, сравнивает
   оригинал/разметку/JSON, структурированный вердикт по каждой маске). Два
   раунда по итогам цикла 2: ямы — good, тёмные трещины — acceptable,
   зафиксированы пропуски детектора и ограничения сегментации. Этот же
   механизм поймал оба ложных эталона.

Запланированная валидация (§11 дизайна, ещё не сделана): mAP на RDD2022
Czech; «золотая» проверка масштаба (ошибка <15% на фото с известным люком);
mask IoU на сегментационном наборе.
