# ТЗ: измерение размеров ямы по фото (длина / ширина / глубина)

Версия 2 (2026-07-14). Заменяет черновик «два фото + EXIF + H=170 см»:
исправлена геометрия глубины, требования по точности приведены в соответствие
с физикой, добавлены протокол съёмки и путь к максимальной точности.

Связанные доки: `PROJECT.md` (принцип честности), `VEHICLE_CAPTURE.md`
(бортовой риг, two-view глубина §3–3.1 — валидирована на синтетике 21/21),
`photogrammetry.py` (прототип v0 математики plane+parallax).

---

## 0. Главный принцип (не подлежит пересмотру)

Система никогда не выдаёт числа, которых физически не может знать.

- Нет подтверждённого метрического якоря → нет СЕРТИФИЦИРУЕМЫХ сантиметров.
  Оценки размеров без якоря допустимы только из явно заданных оператором
  внешних данных (высота камеры — режим A+ ниже), с обязательной меткой
  источника (`metric.scale_source`), `confidence='low'`, полосой ошибки и
  `certifiable=false`; в официальный отчёт такие числа не идут (ред.
  2026-07-16 по итогам адверсариального ревью источника camera_height).
- Глубина в см по **одному** фото невозможна (физика монокуляра) → только
  категория «мелкая / средняя / глубокая».
- Каждое число сопровождается: методом получения, полосой ошибки, флагом
  `certifiable`. Отказ с причиной — **штатный валидный результат**, а не сбой.
- Ложный сантиметр хуже отсутствия сантиметра: система, которая иногда врёт
  на ±5 см, юридически бесполезна для актирования по ГОСТ Р 50597-2017.

## 1. Режимы съёмки и достижимая точность

Точность определяется режимом съёмки, а не «качеством алгоритма».
Требования задаются **по уровням** — система обязана определить свой уровень
по входным данным и не выдавать точность выше него.

| Режим | Вход | Длина/ширина | Глубина | Статус |
|---|---|---|---|---|
| **A** | 1 фото, якоря нет | относительные px | категория (бакеты) | реализовано (pipeline) |
| **A+** | 1 фото + заявленная ВЫСОТА КАМЕРЫ (`--camera-height`; тангаж — по небу в кадре либо из приора той же съёмки) | ОЦЕНКА ±20–40% и семантика маски (Д/Ш = маска с ореолом, не «разрушение») | ОЦЕНКА/верхняя граница (`depth_cm_estimate`) — категория остаётся главным выходом | реализовано (plane_scale.py, 2026-07-16): `scale_source=camera_height`, low, certifiable=false — НЕ для актирования |
| **B** | 1 фото + подтверждённый эталон (люк ГОСТ 3634) | ±2–3 см / ±3–7% | только категория — см невозможны | реализовано (scale.py) |
| **C** | 2 фото с рук «перед/за», якорь есть | как B | классификация порога ГОСТ ≥5 см + полоса ошибки; MAE ≤3 см на принятых; отказы 30–50% — **норма** | математика готова (photogrammetry v0); прогон на архиве 48 ям, снятом ДО протокола: **0 оценок из 95** (`DEPTH_RESULTS.md`) — без соблюдения протокола §3 режим не работает вовсе |
| **D** | серия 6–10 кадров + маркерная доска (протокол §3) | ±1–2 см | **±1–2 см** (цель), p90 ≤2.5 см | не начато — целевой режим ручной съёмки |
| **E** | калиброванный бортовой риг, 2 серии | ±1–2 см | ±0.5–1 см потенциально (синтетика: 0.0–0.3 см) | прототип v0, ждёт пилота — `VEHICLE_CAPTURE.md` |

Запись «±0.5–1 см по глубине» допустима в требованиях **только** для режимов
D/E и только после полевой валидации (§7). Для ручных двух фото (режим C)
такая запись в ТЗ запрещена — она физически не обеспечивается.

## 2. Математика (исправленная относительно v1)

### 2.1. Длина и ширина — плоскость полотна

IPM/гомография «земля → пиксель» — подход верный, но с двумя поправками:

1. **Гомографию строить от якоря, а не от EXIF + «H=170 см».** EXIF-фокус
   смартфонов ненадёжен (мультикамеры, кроп, вычислительная фотография),
   высота с рук гуляет на ±10 см, тангаж произволен. Источник гомографии —
   вписанный эллипс люка (известный круг Ø600) или маркерная доска (§3).
2. Ошибка Д/Ш ограничена снизу не оптикой, а **неопределённостью кромки**:
   у разрушенной кромки «край ямы» сам по себе размыт на 1–3 см. Поэтому
   требование лучше ±1–2 см нефальсифицируемо — принимаем ±2–3 см.

### 2.2. Глубина — НЕ формула параллельного стерео

Формула v1 `D = B·f/Δp` относится к ректифицированной паре с параллельными
осями и к встречной паре «перед/за» неприменима. Правильная модель —
**plane + parallax** (реализована в `photogrammetry.py`):

- точка дна на глубине `dz` ниже плоскости, спроецированная на плоскость,
  смещена К камере: `q = C + (P − C)·h/(h + dz)`;
- для встречной пары при равных высотах камер параллакс направлен вдоль базы
  и не зависит от положения точки: `dz = h·Δ/(B − Δ)`;
- разные высоты камер — численное решение (`solve_depth_from_parallax`);
- при известных позах кадров (режим D) — обычная многовидовая триангуляция
  точек дна + подгонка плоскости полотна по кольцу асфальта вокруг ямы.

**Глубина — величина относительная**: расстояние от точки дна до плоскости
полотна, подогнанной по кольцу вокруг ямы (не «Z-координата точки»).
Итоговая глубина ямы = статистика (median/p90) по **ядру** маски дна
(distance transform), не по склонам — иначе оценка систематически занижается.

### 2.3. База между кадрами

«База автоматически по неподвижным объектам» из v1 — это SfM с масштабной
неоднозначностью: без объекта известного размера база восстанавливается
с точностью до масштаба. Допустимые источники базы, по убыванию точности:
маркер-PnP (§3) → регистрация BEV по текстуре асфальта вокруг ямы (метрика
от риговой/якорной гомографии) → эталонный люк. EXIF и «шаги оператора»
источниками базы не являются.

## 3. Протокол съёмки (здесь выигрывается точность)

Точность глубины определяется на съёмке; софт лишь честно извлекает то, что
в кадрах есть. Протоколы по режимам:

### Режим C — минимальный (2 фото с рук)

1. Два кадра: с подъезда и с противоположной стороны, дистанция 2.5–5 м
   (ближе — сильнее окклюзия дна кромкой; дальше — точность падает как D²).
2. В обоих кадрах — общее кольцо асфальта вокруг ямы и, если есть, люк.
3. Основной объектив (1×), без зума, стоя неподвижно; дно должно быть
   освещено и читаемо. Вода в яме → глубина не измеряется (флаг «вода»).

### Режим D — максимальная точность с рук (целевой)

1. **Маркерная доска**: ChArUco A3/A2, ламинированная на жёсткой основе,
   кладётся на асфальт рядом с ямой (НЕ в яму). Опционально вторая доска
   с противоположной стороны. Доска даёт: метрический масштаб, нормаль
   плоскости полотна и **позу камеры на каждом кадре** (PnP) — исчезают
   разом EXIF, «высота 170 см», масштабная неоднозначность SfM и оценка базы.
2. **Серия вместо пары**: 6–10 кадров дугой вокруг ямы, с 2–3 высот
   (~0.8 / 1.2 / 1.7 м). Низкие кадры усиливают параллакс дна
   (δ = dz·D/h — чем меньше h, тем больше сигнал), высокие — уменьшают
   окклюзию; серия с разных сторон взаимно дополняет затенённые зоны дна —
   снимается главный предел «ровно двух фото» (у ямы глубже 7–8 см при
   съёмке с 4 м взаимно видимой зоны дна для 2 кадров нет вообще).
3. Камера: основной объектив, фиксированный фокус по яме, без HDR-варпа,
   на кадр — остановиться (rolling shutter). Одноразовая калибровка
   интринзиков модели телефона (шахматка) хранится в приложении.
4. Свет: дно читаемо; при глухой тени — дублирующий кадр со вспышкой.

## 4. Функциональные модули

1. **Детекция**: яма / люк / бордюр / маркерная доска (YOLO, существующий
   `detect.py` + класс маркера).
2. **Калибровка**: интринзики из базы моделей телефонов или одноразовая
   калибровка; коррекция дисторсии; позы кадров — маркер-PnP (режим D) или
   якорная гомография (B/C). EXIF — только как затравка, никогда как истина.
3. **Сегментация**: маска ямы (существующий `segment.py`), маска дна,
   кольцо асфальта вокруг ямы.
4. **Реконструкция**:
   - режим C: BEV обоих видов → регистрация по кольцу (аффинная модель
     поглощает ошибку тангажа) → NCC-скан параллакса дна вдоль базы
     (полосовая фильтрация: матчится мм-текстура покрытия, не НЧ-градиенты
     и не изофоты чаши) — как в `photogrammetry.py` v0;
   - режим D: триангуляция плотных соответствий дна при известных позах +
     подгонка плоскости полотна по кольцу.
5. **Измерение**: Д/Ш — экстремумы контура в BEV; глубина — median и p90
   по ядру дна; перевод в вердикт ГОСТ (`severity.py`).
6. **Кросс-чеки** (все обязаны сойтись, иначе отказ):
   - невязка репроекции маркера/люка ≤ порога (px);
   - согласованность dz между независимыми под-парами серии (режим D) ≤ 1.5 см;
   - грубая одновидовая оценка по видимой дальней стенке (высота полосы
     стенки × D/f) согласуется с параллаксной в пределах ×0.5–2;
   - Д/Ш из двух видов согласованы в пределах полосы ошибки.
7. **Гейты честного отказа**: вода (зеркальное отражение неба), взаимная
   невидимость дна, бестекстурное/тёмное дно, рассинхрон калибровки
   (высота/тангаж), развал регистрации кольца, маркер не в кадре (для D).

## 5. Выходные данные

JSON на дефект:

```json
{
  "length_cm": {"value": 78, "ci": 3},
  "width_cm":  {"value": 42, "ci": 3},
  "depth": {
    "category": "глубокая",
    "value_cm": 6.4,          // null, если не измерена
    "ci_cm": 1.8,
    "method": "multiview_marker | two_view_parallax | bucket_relative",
    "certifiable": false,      // true только после полевой валидации (§7)
    "refusal_reason": null     // "вода" | "дно не видно обоим видам" | ...
  },
  "scale_source": "marker | manhole | none",
  "gost_verdict": "..."
}
```

Правило отчёта: `certifiable=false` → в официальный отчёт идёт категория и
(если есть) нижняя оценка «глубина ≥ X см», но не точечное значение.

## 6. Требования к точности (приёмка) — честная редакция

| Величина | Режим | Требование |
|---|---|---|
| Длина/ширина | B–D | MAE ≤3 см при подтверждённом якоре; иначе — только px/категория |
| Глубина | A/B | категория; ошибок «в см» нет, потому что см не выдаются |
| Глубина | C | на принятых парах MAE ≤3 см; ложная классификация порога 5 см («<5 при истине ≥6») ≤5%; доля отказов не нормируется, нормируется их честность |
| Глубина | D | MAE ≤1.5 см, p90 ≤2.5 см, отказы ≤20% при соблюдённом протоколе |
| Глубина | E | по `VEHICLE_CAPTURE.md` (цель ±1 см на порог ГОСТ) |

Запрещено требованиями (и архитектурно):
- глубина в см из одного фото;
- любые СЕРТИФИЦИРУЕМЫЕ см без подтверждённого метрического якоря;
  немаркированная оценка приравнивается к нарушению — оценки существуют
  только с `scale_source`/`confidence=low`/полосой (режим A+, §0);
- точечная глубина без полосы ошибки;
- «средняя точность ±0.5 см» для ручной съёмки — критерий из v1 удалён как
  физически не обеспечиваемый.

## 7. Валидация (обязательная, гейтит `certifiable`)

1. Полевой набор: ≥30 ям разных форм/глубин (3–15 см), включая колейные.
2. Ручной эталонный замер: рейка поперёк ямы + линейка в максимум глубины
   (фото замера сохраняется как ground truth).
3. Съёмка тех же ям по протоколам C и D тремя разными операторами и
   ≥2 моделями телефонов.
4. Метрики: MAE, p90, доля отказов, матрица классификации порога 5 см.
5. `depth_certifiable=true` включается ТОЛЬКО после прохождения п. 1–4
   в допусках §6. До этого — жёстко `false` (как в `photogrammetry.py` v0).

## 8. Путь к максимально точной глубине (сводка решений)

Лестница точности — чем ниже пункт, тем точнее и дороже:

1. **Маркерная доска в сцене** (режим D) — главный дешёвый выигрыш:
   метрические позы кадров через PnP убирают все крупные источники ошибки
   разом (EXIF, высоту, базу, масштаб SfM). Себестоимость — ламинированный
   лист и +60 секунд на съёмку. Ожидаемо ±1–2 см.
2. **Серия с разных высот и сторон вместо «ровно 2 фото»** — закрывает
   взаимную окклюзию дна (главный предел двух кадров) и даёт √N-выигрыш
   по шуму + внутренний кросс-чек между под-парами.
3. **VIO-позы телефона (ARCore/ARKit)** — метрические позы без маркера
   (масштаб от IMU, дрейф ~1–2%): fallback режима D, когда доску не положили.
4. **LiDAR/ToF телефона, где есть** (iPhone Pro, часть Android): прямая
   метрическая глубина ±~1 см на дистанции 1–3 м — использовать как
   независимый источник и кросс-чек параллакса; вода остаётся непреодолимой.
5. **Калиброванный бортовой риг** (режим E, `VEHICLE_CAPTURE.md`): жёсткая
   геометрия + серии из потока → потолок пассивной фотограмметрии
   (на синтетике 0.0–0.3 см; реальный пилот обязателен).
6. **Активный профилометр (лазер/структурированный свет)** — вне рамок
   данного ТЗ; единственный путь к гарантированным ±0.5 см «всегда».

Во всех пунктах сохраняется правило §0: если условия пункта не выполнены —
система опускается на уровень ниже или честно отказывает, а не экстраполирует.
