# Сбор и разметка собственного датасета

**Обновлено:** 2026-07-03.
Этот документ — полный протокол: как снимать, что записывать, как хранить,
как размечать и как скормить проекту. Дополняет `PAIR_WORKFLOW.md` (там —
запуск парного режима и метрики качества); здесь — сам сбор данных.

**Почему это самая важная часть.** Всё, что сейчас ограничивает проект,
упирается в данные, а не в код:

| Потребитель | Что ему нужно | Что без него не работает |
|---|---|---|
| Дообучение детектора | 150–300+ кадров с разметкой боксов | честная точность на дорогах РФ (Czech-метрики train-contaminated) |
| Парный сценарий (F1) | пары front/back + правда «есть/нет дефект» | recall/precision слияния двух видов |
| «Золотая» валидация масштаба (§11) | фото с люком/эталоном + рулеточные замеры | включение эталонов разметки/борта/блоба по умолчанию |
| Калибровка бакета глубины | заведомо ГЛУБОКИЕ ямы косым ракурсом | пороги v0 остаются некалиброванными (прогон 2026-07-03: на демо-фото модель глубины вообще не видит ям рельефом) |
| Сценарий C (будущее) | серии 10–15 кадров с перекрытием | сертифицируемая глубина в см |

Один выезд по протоколу ниже кормит всех потребителей сразу.

---

## 1. Оборудование и настройки

- Телефон с нормальной камерой. **Максимальное разрешение, без зума**
  (цифровой зум портит текстуру трещин), объектив протереть.
- Геометки (GPS в EXIF) — **включить**: пригодятся подсистеме карты, а время
  съёмки свяжет кадр с журналом.
- Рулетка 3–5 м и жёсткая рейка/палка длиннее ямы (глубина меряется так:
  рейка поперёк ямы, рулетка от рейки до дна в самой глубокой точке).
- Блокнот или заметки в телефоне для журнала (или сразу таблица, см. §4).

## 2. Протокол съёмки одного дефекта (~3 минуты)

Порядок кадров важен, чтобы потом не путаться в галерее.

1. **`front.jpg`** — основной вид «спереди»: стоя в 2–4 м от дефекта, камера
   под **~40–60° к поверхности** (естественный взгляд стоящего человека).
   Дефект целиком в кадре + 1–2 м асфальта вокруг него.
2. **`back.jpg`** — то же самое с противоположной стороны дефекта.
3. **Кадр с эталоном** (если рядом есть люк, чёткая разметка или бордюр):
   дефект и эталон в одном кадре. Люк — лучший эталон; серый люк на сером
   асфальте тоже снимай (пойдёт в набор для будущего класса «люк»).
4. **Для глубокой ямы (на глаз ≥5 см)** — дополнительный акцентированный
   косой кадр, где виден рельеф дна (свет сбоку лучше, чем плоский полдень).
5. **Кадр с рулеткой/рейкой в яме** — в отдельную папку `gt_photos`
   (в обучающие кадры измерительные инструменты попадать не должны).
6. **Для 3–5 самых выразительных ям за выезд** — серия для Сценария C:
   10–15 кадров, обходя яму по дуге, каждый следующий кадр перекрывает
   предыдущий на ~70%. Дистанция 1.5–3 м, высота та же.

### Чего избегать

- **Надир (строго сверху вниз) как основной ракурс.** Проверено кодом и
  ревью 2026-07-03: без перспективы в кадре линейка глубины честно
  отказывает, а модель монокулярной глубины на плоском ракурсе слепа.
  Косой кадр обязателен; надирный можно добавить шестым, но не вместо.
- Съёмка «издалека на всякий случай»: если дефект занимает <5% кадра,
  детектору и сегментатору почти нечего есть. Подойди ближе.
- Только «красивые» ямы в солнечный день. Нужны и тени, и пасмурно, и
  мокрый асфальт, и вечер — иначе модель развалится вне идеальных условий.
- Свои ноги/тень в кадре над дефектом.
- Лица людей и номера машин крупным планом (или потом блюрить — важно,
  если данные когда-нибудь будут передаваться).

## 3. Структура папок

```text
datasets/
  local_pairs/            # пары для --pairs-dir (структура уже поддержана CLI)
    001/
      front.jpg
      back.jpg
      context_manhole.jpg # доп. кадры не мешают: CLI берёт только front/back
    002/
      ...
  local_series/           # серии для будущего Сценария C
    001/                  # тот же id, что и в local_pairs, если это та же яма
      s01.jpg ... s15.jpg
  gt_photos/              # кадры с рулеткой/рейкой — НЕ для обучения
    001_ruler.jpg
  journal.csv             # журнал (см. ниже)
```

Канонические имена — именно `front`/`back` (алиасы `1/2/a/b` поддержаны, но
канонические имена главнее и надёжнее). `datasets/` в git не попадает
(`.gitignore`) — храни копию на внешнем диске/облаке.

## 4. Журнал — половина ценности датасета

Без записанных руками размеров фото остаются картинками; с ними — это
валидационный набор с ground truth. Одна строка на дефект:

```csv
id,scene,date,street_or_gps,type,length_cm,width_cm,depth_cm,reference_in_frame,weather,notes
001,001,2026-07-05,ул. Ленина 12,pothole,42,31,6.5,manhole,sunny,яма у люка
002,002,2026-07-05,55.7522 37.6156,pothole,28,19,3,none,sunny,
003,003,2026-07-05,ул. Ленина 30,long_crack,180,2,,none,sunny,трещина вдоль колеи
```

Правила:

- `scene` — id сцены: соседние дефекты, снятые ОДНИМ общим кадром front,
  получают общую сцену (наименьший id группы). Заполняет
  `scripts/ingest_local_pairs.py` автоматически (группировка по md5 кадра).
  По сценам считается честный recall (`scripts/pair_quality_table.py`) и
  делается train/val-сплит без утечки одинаковых кадров (§6).
- `depth_cm` — по рейке+рулетке, самая глубокая точка. Для трещин пусто.
- `type` на этом этапе достаточно грубого: `pothole / long_crack /
  trans_crack / alligator / patch` (маппинг на классы модели — в §6).
- `reference_in_frame`: `manhole / marking / curb / none` — по этому полю
  потом отбирается набор для «золотой» валидации масштаба.
- Заполняй на месте, не «вечером по памяти».

## 5. Объёмы и приоритеты

| Этап | Что | Сколько | Что разблокирует |
|---|---|---|---|
| 1 | Пары front/back с замерами (начать с ям) | 20–30 пар | первая честная таблица recall/precision (`PAIR_WORKFLOW.md` §«Как понять качество») |
| 2 | Заведомо глубокие ямы (≥5 см), косой ракурс | 10–15 шт | калибровка порогов бакета глубины (`scripts/calibrate_depth_bucket.py`) |
| 3 | Дефект + люк в кадре, с рулеточными замерами | 5–10 шт | «золотая» валидация масштаба: ошибка <15% → включение доп. эталонов |
| 4 | Кадры под разметку боксов (входят и все кадры этапов 1–3) | 150–300+ | дообучение детектора на РФ-данных |
| 5 | Серии с перекрытием | 3–5 ям × 10–15 кадров | задел на фотограмметрию (Сценарий C) |

Разнообразие важнее объёма: 150 кадров с 10 улиц в 4 погодах полезнее
500 кадров одного двора в один день.

## 6. Разметка для дообучения детектора

### Классы

Разметка ведётся в таксономии весов rezzzq (RDD2022), id менять нельзя:

| id | Код RDD | Класс проекта | Что это |
|---|---|---|---|
| 0 | D00 | longitudinal_crack | трещина ВДОЛЬ направления движения |
| 1 | D10 | transverse_crack | трещина ПОПЕРЁК |
| 2 | D20 | alligator_crack | сетка трещин («крокодилова кожа») |
| 3 | D40 | pothole | яма |
| 4 | Repair | patch | заплатка / след ремонта |

### Инструмент

- **CVAT** (https://www.cvat.ai — есть бесплатный SaaS и self-hosted) —
  удобен, если размечать будут несколько человек; экспорт «YOLO 1.1».
- **LabelImg** или **AnyLabeling** — проще для одного человека, локально,
  сразу пишут YOLO txt.
- Установка разметчика — вне venv проекта (это отдельный инструмент, в
  зависимости движка он не входит).

### Правила разметки боксов

1. Бокс — тесно по видимой границе дефекта, без «запаса».
2. Каждый отдельный дефект — отдельный бокс. Перекрывающиеся боксы — норма.
3. Непрерывная длинная трещина — ОДИН бокс на всю видимую длину, не куски.
   Если трещина реально прерывается асфальтом — это разные боксы.
4. Сетка трещин (D20) — один бокс на связную область сетки, не каждая
   трещинка внутри.
5. Яма, засыпанная светлым материалом, — всё равно D40 (именно такие модель
   сейчас пропускает — они самые ценные для дообучения).
6. Заплатка поверх старой ямы — Repair; если в заплатке новая яма — два
   бокса (Repair + D40).
7. Мелочь короче ~15 px по длинной стороне кадра не размечать.
8. Сомневаешься в классе — размечай ближайшим по смыслу и ставь пометку в
   журнал; сомневаешься «дефект ли это вообще» — НЕ размечай (лучше чистый
   негатив, чем шумная метка).
9. Кадры без дефектов (10–20% набора) остаются с пустым txt — это
   негативы, они учат модель не галлюцинировать.

### Формат и раскладка

YOLO-формат: на каждый `images/**/x.jpg` — файл `labels/**/x.txt`, в каждой
строке `class cx cy w h` (нормированные 0..1). Раскладка и `data.yaml` — те
же, что делает `scripts/prepare_rdd2022.py` для RDD2022:

```text
datasets/local_rf_yolo/
  images/train/*.jpg      images/val/*.jpg
  labels/train/*.txt      labels/val/*.txt
  data.yaml
```

```yaml
# datasets/local_rf_yolo/data.yaml
path: C:/Users/Kordon/doroga_govna/datasets/local_rf_yolo
train: images/train
val: images/val
names:
  0: D00
  1: D10
  2: D20
  3: D40
  4: Repair
```

### Train/val: делить по ЛОКАЦИЯМ, не по кадрам

Критично против утечки: `front.jpg` и `back.jpg` одного дефекта (и все
кадры одной серии) обязаны попасть в ОДИН сплит. То же про сцены: у соседних
дефектов front/back могут быть ОДНИМИ И ТЕМИ ЖЕ файлами (колонка `scene`
журнала, §4) — вся сцена целиком идёт в один сплит. Правильное деление — по
улицам/дням: например, все кадры двух улиц целиком в val (~10–15% кадров),
остальное в train. Случайное перемешивание кадров даст фиктивно высокий
mAP — та же ловушка, что train-contamination Czech (STATUS, цикл 3).

## 7. Дообучение и проверка

```powershell
cd C:\Users\Kordon\doroga_govna

# дообучение от чекпоинта rezzzq (freeze-слои по умолчанию)
.\.venv\Scripts\python.exe scripts\finetune_rdd2022.py --data datasets\local_rf_yolo\data.yaml --epochs 50 --imgsz 1024

# смок-проверка самого конвейера без данных (синтетика, ~30 с).
# --no-install ОБЯЗАТЕЛЕН: без него toy-веса встанут в models/finetuned_best.pt
# и реестр молча сделает их основным детектором для всех запусков CLI
.\.venv\Scripts\python.exe scripts\finetune_rdd2022.py --make-toy 24 --epochs 2 --no-install
```

Честно про железо: на этой машине (CPU) 50 эпох × 300 кадров — это ночь и
дольше; настоящий прогон лучше делать на любой машине с GPU (можно бесплатный
Colab: залить `datasets/local_rf_yolo` + чекпоинт, вернуть `best.pt`).
На Colab/Linux сначала поправь в `data.yaml` строку `path:` — абсолютный
Windows-путь `C:/...` там не существует, укажи путь к папке на той машине.
После обучения веса ставятся в `models/finetuned_best.pt` и реестр подхватит
их первым кандидатом (`--no-install`, чтобы этого не делать).

Сравнение до/после — на СВОЁМ val-срезе (не Czech!) и на парах:

```powershell
$env:PYTHONPATH="src"
.\.venv\Scripts\python.exe -m road_defect.cli --pairs-dir datasets\local_pairs --output outputs_pairs --ensemble
# сводка: outputs_pairs\pairs_summary.csv; сверить с datasets\journal.csv
```

Разбор ошибок по группам (пропуск / лишний объект / плохой контур) — см.
`PAIR_WORKFLOW.md`. Худшие 5–10 пар копируй в `datasets/local_pairs_hard` —
это регрессионный набор следующих циклов.

## 8. Спец-наборы: глубина и масштаб

- **Глубина.** Из этапа 2 (глубокие ямы): сначала прогнать пары через
  `--pairs-dir` (отчёты лягут в `outputs_pairs`), затем:

  ```powershell
  .\.venv\Scripts\python.exe scripts\calibrate_depth_bucket.py outputs_pairs
  # если отчёты одиночные (--input) и фото не в корне проекта:
  .\.venv\Scripts\python.exe scripts\calibrate_depth_bucket.py outputs_ямы --images=datasets\deep_pits
  ```

  Скрипт покажет по каждому дефекту `_drop` против шума — то есть кодирует
  ли Depth Anything рельеф вообще, — и если да, даст данные для настоящей
  калибровки порогов `BUCKET_LO/HI` (сейчас v0, физически мотивированы).
  Если и на явных ямах сигнала нет — это честный аргумент закрывать вопрос
  глубины только Сценарием C.
- **Масштаб.** Из этапа 3 (дефект + люк + рулеточные замеры). Важно про
  ожидания: с дефолтными флагами масштаб выдаёт только Hough-люк, а он на
  косых смартфонных кадрах и серых крышках почти никогда не подтверждается
  (за всю историю проекта — ни разу на реальном фото; STATUS, циклы 1–4).
  Поэтому валидационный прогон — с включёнными экспериментальными путями,
  которые этот этап и должен проверить:

  ```powershell
  $env:PYTHONPATH="src"
  .\.venv\Scripts\python.exe -m road_defect.cli --input datasets\scale_shots --output outputs_scale --blob-ref --marking-ref --curb-ref
  ```

  Сравнить `metric.*_cm` с журналом; `scale.note` в JSON объясняет, какой
  эталон сработал и почему. Цель §11 — ошибка <15%; только после этого
  какие-то из флагов имеет смысл включать по умолчанию. Если масштаб честно
  не выдан (`metric.available=false`) — это тоже результат: он показывает,
  что для сантиметров нужен класс «люк» в детекторе (роадмап).

## 9. Частые вопросы

- **Сколько всего надо в итоге?** Для уверенного дообучения ориентир —
  500–1000 размеченных кадров, но первые выводы (и первый прирост) даст
  уже этап 4 в 150–300. Собирать лучше итерациями: снял 30 пар → прогнал →
  посмотрел ошибки → следующий выезд закрывает именно их.
- **Можно ли брать фото из интернета?** Для обучения — осторожно
  (лицензии), для валидации — нет: нужны твои дороги, твой телефон и твоя
  рулетка, иначе ground truth нет.
- **Видео вместо фото?** Можно (кадры нарезаются), но смаз и сжатие хуже;
  для серий Сценария C отдельные фото с перекрытием надёжнее.
- **Зима?** Снег скрывает дефекты — сезон сбора ограничен; тем ценнее
  успеть набрать разнообразие до зимы.
