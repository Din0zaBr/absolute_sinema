# Eval-набор детекции (P0): протокол замера precision/recall и FP-категорий

Зачем: до этого замера любые правки детекции — угадайка (IMPROVEMENTS.md, P0).
mAP на RDD2022-Czech train-contaminated и годится только как смок. Здесь —
локальный **held-out** набор с ручной разметкой и харнесс, считающий
precision/recall по классам и **долю FP по категориям** (авто / вне дороги /
заплатка / тень-бордюр / край / дубль / прочее).

⚠️ **Набор НАМЕРЕННО смещён к конфузорам**: 40 из 46 кадров — сцены, где
модель уже ошибалась (карта FP), «чистых» только 6. Абсолютные precision/recall
на нём пессимистичны для «средней улицы», а эффект таргетного фикса —
оптимистичен. Числа валидны ТОЛЬКО для сравнения «до/после» НА ЭТОМ наборе и
для приоритизации FP-категорий; цитировать их как «общую точность системы»
(в отчёты руководству и т.п.) — нельзя.

## Дисциплина held-out (не нарушать)

- Сцены eval-набора **никогда не попадают в обучение**. Список —
  `datasets/eval_v1/holdout_scenes.txt`; `scripts/prepare_local_finetune.py`
  исключает их автоматически: по id (вместе со всей md5-группой сцены) И по
  СОДЕРЖИМОМУ (кадр, байт-в-байт совпадающий с eval-кадром из manifest, не
  пройдёт ни под каким id). Статус гейта печатается в КАЖДОМ прогоне — если
  видишь `[!] holdout-гейт НЕАКТИВЕН`, остановись и собери набор. Явно
  указанный, но несуществующий `--holdout` — ошибка, а не отключение;
  отключение — только `--holdout ''` (печатается громко) и только если
  понимаешь, что делаешь.
- Гейт живёт в prepare_local_finetune: запуск `finetune_rdd2022.py --data` с
  самодельным/чужим data.yaml минует его — не делай так для наборов,
  пересекающихся с eval-сценами.
- Набор не растить синтетикой и не «чистить» под желаемые метрики. Кадры
  добавлять можно (лучше — новые съёмки конфузоров), удалять — нельзя; харнесс
  сверяет разметку с manifest и печатает выпавшие кадры в каждом замере.
- Ground truth — только ручная разметка. Предложения движка в разметчике — НЕ
  разметка, пока человек их явно не принял.

## Версионирование и бэкап

`manifest.csv`, `holdout_scenes.txt` и `annotations.json` — малые текстовые
носители held-out дисциплины, они **версионируются** (исключения в
`.gitignore`): свежий клон не теряет ни гейт, ни разметку. **После разметки
закоммить `datasets/eval_v1/annotations.json`** — это 2–4 часа ручной работы,
localStorage браузера ей бэкапом не является. Кадры `frames/` — бинарники вне
git; набор воспроизводится `make_eval_set.py` при наличии исходников
(`datasets/local_pairs`, корневые демо-фото).

## Конвейер (4 шага)

```powershell
# 1. Скелет набора: кадры сцен из карты FP + демо, manifest, holdout-список
.\.venv\Scripts\python.exe scripts\make_eval_set.py

# 2. Прогон движка по кадрам (той же конфигурацией, что и в бою)
$env:PYTHONPATH="src"
.\.venv\Scripts\python.exe -m road_defect.cli --input datasets\eval_v1\frames --output outputs_eval\reports

# 3. Разметчик: открыть outputs_eval\annotator.html, разметить, скачать
#    annotations.json и положить в datasets\eval_v1\annotations.json
#    (альтернатива: внешняя программа — выбран X-AnyLabeling — затем
#    scripts\import_annotations.py; см. docs/ANNOTATION_GUIDE.md)
.\.venv\Scripts\python.exe scripts\build_eval_annotator.py --proposals outputs_eval\reports

# 4. Замер (повторять после каждого изменения детекции)
.\.venv\Scripts\python.exe scripts\eval_detection.py
```

Сравнение «до/после» правки: прогнать шаг 2 в ДРУГУЮ папку (например
`outputs_eval\reports_fix`), затем `eval_detection.py --reports <папка> --out
<папка_метрик>` — разметка одна, отчёты разные.

## Как размечать (разметчик `outputs_eval/annotator.html`)

Размечаешь впервые — начни с пошаговой инструкции **`docs/ANNOTATION_GUIDE.md`**
(без жаргона: что открыть, какой класс выбирать, разбор сомнительных случаев).
Ниже — краткий протокол.

Офлайн-страница: слева список кадров, в центре canvas. Боксы хранятся в
**пикселях оригинала** (страница показывает ужатую копию, пересчёт зашит).
Автосохранение в localStorage браузера; «Скачать annotations.json» — экспорт.

- **Дефекты** (сплошные рамки): режим «дефект», классы `pothole / patch /
  longitudinal_crack / transverse_crack / alligator_crack`. Размечаем всё, что
  дорожный инспектор назвал бы дефектом на проезжей части. Заплатку размечаем
  как `patch` (модельное «pothole» на ней харнесс посчитает FP категории
  `gt_patch` — это и есть категория «заплатка» из карты FP).
- **Конфузоры** (пунктирные рамки): режим «конфузор», категории `car`
  (машина/колесо/фара), `off_road` (стены, клумбы, плакаты — всё вне проезжей
  части), `shadow_curb` (тень, бордюр/лоток), `other`. Обводить ЗОНЫ, где
  модель ошибалась или может ошибаться; FP внутри такой зоны получает её
  категорию автоматически. Категория `edge` (мелочь у кромки кадра) считается
  геометрией — размечать не нужно.
- **Предложения движка** (серый пунктир, `label 0.71?`) — подсказки из шага 2:
  Enter/кнопка «Принять» превращает в дефект, Del отклоняет. Непринятые в
  экспорт НЕ попадают.
- Кадр закончен → галочка **«кадр размечен»**. В метрики идут ТОЛЬКО такие
  кадры (`status="reviewed"`); черновики харнесс пропускает и сообщает об этом.
- Кадр без дефектов — это ЦЕННЫЙ негатив: просто пометь его размеченным.
- Черновик живёт в localStorage с ключом от СОСТАВА набора: при изменении
  состава (пересборка make_eval_set с другими сценами) старый черновик не
  подхватится — сначала «Скачать annotations.json», положить в eval_v1, и
  пересобранная страница подхватит его как встроенную разметку.

## Схема `datasets/eval_v1/annotations.json` (version 1)

```json
{"version": 1, "frames": {
  "<frame_id>": {
    "image_size_px": [W, H],
    "status": "reviewed" | "draft",
    "defects":   [{"label": "pothole|patch|longitudinal_crack|transverse_crack|alligator_crack",
                   "bbox_xywh": [x, y, w, h]}],
    "confusors": [{"category": "car|off_road|shadow_curb|other",
                   "bbox_xywh": [x, y, w, h]}],
    "note": "",
    "proposals_resolved": ["служебное: сигнатуры решённых предложений движка"]
}}}
```

Все координаты — пиксели ОРИГИНАЛА, `[x, y, w, h]`, `w/h > 0`. Валидацию
делает `eval_detection.load_annotations` (неизвестный класс/категория или
вырожденный бокс валят замер с указанием кадра — чинить разметку, не харнесс).
Файл создаёт наш разметчик («Скачать annotations.json») либо конвертер
внешней разметки `scripts/import_annotations.py` (родной формат
X-AnyLabeling / YOLO / COCO) — он гоняет результат через тот же
`load_annotations` и при любой проблеме не пишет ничего.

## Как читать отчёт `eval_detection.py`

- Таблица по классам: GT/TP/FP/FN, precision = TP/(TP+FP), recall = TP/GT.
  Сопоставление: жадное по убыванию confidence, IoU ≥ 0.5, только одинаковый
  класс.
- «FP по категориям»: `gt_<класс>` — misclass по разметке (яма на заплатке);
  `car / off_road / shadow_curb / other` — по конфузорам (бокс ≥ 50% внутри
  зоны); `duplicate` — второй бокс на ту же GT; `edge` — мелочь у кромки
  (эвристика v0: касается полосы 2% кадра и ≤ 6% меньшей стороны); `unknown` —
  остальное. Это прямая приоритизация P1-гейтов из IMPROVEMENTS.md.
- CSV для разбора руками: `outputs_eval/eval_summary.csv` (сводка),
  `eval_fp.csv` (каждый FP с категорией — источник hard-negative кропов для
  P4), `eval_fn.csv` (каждый пропуск — кандидаты в recall-меры P2).
- Честные правила: reviewed-кадр без отчёта движка — ошибка (непрогнанный кадр
  ≠ «ноль детекций»), обход только явным `--allow-missing` — и учти: GT таких
  кадров уходят в FN (recall честный), но их несостоявшиеся FP в замер не
  попадают — **precision может быть завышен**, сравнение «до/после» с разным
  составом отчётов невалидно. Грязная разметка (неизвестный класс, вырожденный
  бокс) валит замер с указанием кадра. Пороги замера печатаются в шапке и
  пишутся в `outputs_eval/eval_params.json` — «до/после» сравнивать только при
  одинаковых параметрах; покрытие набора сверяется с manifest в каждом прогоне.
